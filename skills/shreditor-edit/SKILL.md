# Shreditor edit

You are the agent half of Shreditor: you make the edit, the user previews and adjusts it in the Shreditor editor, and each next pass starts from their saved state. The design behind this is in the Shreditor repo under `agent/`; this file is how to run it.

**Rules that are not negotiable**

1. **Every engine call goes through `shred`** (`node <this skill>/scripts/shred.mjs`). Never hand-roll HTTP calls, write `project.json`, or invent ops. If `shred` can't do something, say so and stop.
2. **Never build in the user's project.** Build on a draft (`shred draft`), verify it, then hand it over with `shred publish`. The user sees finished passes only, never work in progress.
3. **The user's tweaks are decisions.** Before every pass, `shred changes` shows what they changed; keep it. Never reapply an old plan over their edits.
4. **The format comes first, the style second, neither is yours to invent.** Choose the format with the user before anything else (step 1). Load the style skill before planning. Landforce: read `~/Dev/landforce/.claude/skills/landforce-vlog/SKILL.md` and the kit it names. No style skill: ask once, record the answer in the brief.
5. **A command succeeding is not a check.** Open every rendered image you rely on. Say plainly what you looked at, listened to, or didn't.

**Setup, every session:** `shred status`. If its `login` line says `none`, installing is your job, not the user's: run `node <repo>/bin/shreditor.mjs install --yes` (the repo is three levels above this skill's `scripts/`; `npx shreditor` only works from inside the repo). It checks and fixes what Shreditor needs (ffmpeg and whisper.cpp through Homebrew, the transcription model, dependencies, the build) and adds login items that keep the editor (http://localhost:5273) and the agent service running from then on. Tell the user in one line what it set up. It can't install Homebrew, Chrome or Node: if one is missing, tell the user exactly what to install, then run it again. With the login items in place, `shred` commands start anything that's down on their own. Don't open the editor at setup. The edit starts in the chat: the user gives you clips, you catalog, agree the format and plan. The editor is where they review and tweak a pass, so open it at the first `shred publish` (step 4), not before. Then open it for the user yourself: if you have a built-in browser (the Claude desktop app's browser pane), open the editor URL there so it sits beside the chat; otherwise give the link (it needs Chrome or another Chromium browser; the user can also install it as the Shreditor app from Chrome). A link the user clicks opens in their default browser, not your pane. The workspace (where projects, media and catalogs live) is `~/Movies/Shreditor` unless `~/.shreditor/config.json` says otherwise; `SHRED_WORKSPACE=<dir>` overrides both (tests and scratch work).

## The loop

### 1. Choose the format

Every edit starts here; nothing is planned or cut until the format is agreed. A format defines the whole project: canvas, named tracks, pacing, text and audio rules, and the targets `shred check` scores. There are four (`shred format list`):

| Format | Use when | Variants |
|---|---|---|
| Graphic Yap (`graphic-yap`) | Talking head in a real setting, naming things that can be shown as images | `standard` (default), `intense` |
| Greenscreen Talking Head (`greenscreen`) | Talking head shot on a green screen, or meant to be keyed | |
| Vlog (`vlog`) | B-roll with voiceover narrating over it | `fast`, `slow` (pick one) |
| 10 Shot (`ten-shot`) | Clips of a place, thing or experience; nobody talking; music | `even`, `beat`, `shaped` (rhythm) |

- If the user named one, use it; if the footage doesn't fit it, say so before editing. Otherwise catalog first (step 2): `shred catalog` prints a suggested format with its reason. Propose one format and variant with a one-line reason from the footage and get the user's yes. The decision rules and tie-breakers are in `<repo>/formats/choosing.md`.
- Record it: `shred new --name "..." --format <id> [--variant <v>]` (sets the canvas and creates the format's named tracks, each with its role), or `shred format set <projectId> <id> [--variant <v>]` on an existing project.
- If the user has a Video Style Kit (`kit.json`), apply it once: `shred kit apply <kit.json|kit folder> --project <id>`. Use its styles for titles, captions and overlays (`kit:title`, `kit:caption` / `kit:caption-low`, `kit:overlay`, `kit:listicle-headline`, `kit:emphasis`), and follow the kit's preferences over the format's defaults (apply and `shred kit status` print them). `shred check` includes the kit's rules. Never edit `kit.json` unless the user asks; then `shred kit save-back <id>` (their style tweaks in the editor) or `shred kit set <id> <path> <value>` (a value by path: `titles.style.size 104`, `fonts.classic.stack.0 "TikTok Sans"`), never by hand.
- `shred format <projectId>` prints the format's rules, targets, checklist and guide path. **Read the guide (`formats/<id>/guide.md`) fully before planning.** It is the source of truth; its targets and rules drive the plan. Ignore what it says about other plugin skills or tools: here every edit goes through `shred`.

### 2. Catalog the footage

- `shred catalog <folder or files> --name <slug>` probes everything, makes a contact sheet per clip, transcribes speech (whisper.cpp) and suggests a format. Output: `<workspace>/catalogs/<slug>/catalog.json` plus `sheets/` and `transcripts/`. Footage already imported is not transcribed again: its entry carries `mediaId`, the built-in transcript and any `category` with its `categorySource`.
- Every audio/video import is transcribed in the background on its own (whisper.cpp, locally, word timings), into the same transcript the editor's transcript panel and captions use. `shred transcript <mediaId>` prints its words with start/end seconds (`--json` for segments); it says `queued`/`running` while still working and `none` when there is no speech. `shred transcribe <mediaId>` runs it now. If it says unavailable, `shred setup` (then `--yes` to download the model, with the user's OK).
- Open every contact sheet and read every transcript. Add to each catalog entry: `content` (what it shows, in a few words), `best` (in-points worth using, seconds), `usable` (yes/no and why), `category`, and for talking heads where the face sits. Metadata does not tell you what a shot shows.
- `category` is what the file is for: `speaker` (talking head), `b-roll`, `graphics` (screenshots, evidence, title cards), `overlay` (transparent cutouts, animated overlays), `voiceover`, `music`, `sfx` or `other`. Every entry gets one; the scorecard maps categories to the format's roles. Apply them when you import; the editor's media pane groups by them. With a project open, the editor suggests `speaker` or `b-roll` for uncategorized video on its own (`categorySource: auto`, shown as `[speaker auto]` by `shred media --project <id>`). A suggestion is a guess from speech and frames: confirm it or correct it with `shred categorize`, which makes it yours.
- `browserPlayable: false` (PNG-codec `.mov`, DNx, MPEG-4 Part 2, AVI/MTS, AC-3/ALAC audio, ...) needs nothing from you: import makes a working copy automatically (`workingCopy` says how). ProRes reports `true`: the editor decodes it itself. Always import the original file. Transparent video keeps its alpha, so cutouts and overlays stay separate, movable layers. Originals are never touched.
- After importing, `shred qc --project <id>` measures each clip's sound and picture and prompts where to look or listen (noise, pops, clipping; dark, flat, colour cast). Note what needs attention in the catalog; correction happens in the edit, only where it's needed.
- Entries with `speechNote` had no real speech (Whisper's "Thank you." on music or typing is discarded). Flag duplicates.
- Give the user a short catalog summary: what's there, what's strong, what's missing, and the format you propose.

### Starting from a reference video

When the user wants their footage cut like a proven video (a VideoDatabase link or id, "like this one", "recut last week's 10 Shot with this new footage"), make an edit template from it and plan from that. A template is the reference's structure and pacing targets as slots (shots with roles and lengths, texts with their pattern and style, graphics, captions), never timings to copy: VideoDatabase timings are AI-labeled, and the new cut follows its own footage and speech.

- **VideoDatabase:** call the VideoDatabase MCP `get_video_dna` with `format: "json"` (resolve a link with `resolve_video` first), save the response as `<workspace>/projects/<id>/agent/reference/vdb-<videoId>.json`, then `shred template from-vdb <that file>`. A Video DNA `.md` the user downloaded works the same way. No edit timeline in the DNA means there is nothing to template: say so.
- **A finished project:** `shred template from-project <projectId>`; `shred new --from-template <name> --name "..."` rebuilds its tracks, text styles and timeline with every clip a slot still playing the old media, and `shred template fill <newId> --slot s03=<mediaId>[@inSec] ...` swaps new media in (ids and timing kept; media too short for the slot is refused). Rewrite the texts, add captions again, then check.
- Show the user the slot table (`shred template show <name>`) and the format it suggests with its reason; agree the format as in step 1 (`shred new --from-template <name>` creates the project in it).
- `shred plan <id> --template <name> [--request "<their words>"]` (the request is optional) writes the plan: for Vlog and 10 Shot a beat per shot slot with candidate clips by category; for Graphic Yap and Greenscreen the speaker's performance from their transcript, with the template's cutaways, graphics, title and labels placed on the kept lines at the same share of the runtime. Review it like any scaffold, replace the `[PLACEHOLDERS]` in the texts, then `shred plan` and build as usual. `shred check` adds a Template section (cuts per minute, median and first shot, shot mix, labels, title from frame 0 and its hold, captions): information, not rules. Each line is close to the reference or differs from it; a difference is not a miss to fix or explain, since the cut follows the new footage. Most edits use no template.

### 3. Plan

- Ask what the format and style skill don't settle, if the user hasn't said: length, audience, the one thing the viewer should leave with, must-keep moments, and whether they want to see the plan first. One round of questions, only what changes the result.
- Import the footage you'll use, one call per category: `shred import <files> --project <id> --category <category>` (clones in place, no copying; it waits while files Chrome can't decode get their working copy, printing progress). Fix or add categories later with `shred categorize <mediaId>=<category> ...`. The open editor shows imports and category changes within a second. The user can recategorize from a media card; their choice is in `media/<id>/metadata.json` and wins.
- Vlog with a script but no recorded VO: rough the cut out on a scratch voiceover, `shred tts --project <id> --file script.txt` (local TTS, imported as `voiceover`, marked scratch in its metadata; `references/engine.md`, Scratch voiceover). It is a placeholder for timing only: label it as one in `summary.md` and the hand-over, and never present it as the final VO.
- **The first edit is always built from a plan.** The order is fixed: catalog (step 2) → brief → plan → `shred plan` → [plan review] → `shred draft` → `shred build` → refine → `shred check` → publish. `shred draft` refuses a project's first pass until its plan validated clean.
- Write the brief: `<workspace>/projects/<id>/agent/brief.yaml` (template: `references/brief-and-plan.md`).
- Write the plan: `<workspace>/projects/<id>/agent/plan.json` (schema v3, `references/brief-and-plan.md`). Either way it starts with the user's `request` in their words and the `story.arc` (the order of the video and why, in a sentence or two) with its `structure` (the format's roles: `shred format <id>` and the guide's Structure, e.g. hook → body → close). What follows depends on the format:
  - **Graphic Yap and Greenscreen: the plan is the performance** (`mode: "performance"`). The speaker's take is the spine; the plan lays out their lines, which to keep, and what goes on screen with each. Start with `shred plan <id> --scaffold <speaker mediaIds, in play order>`: it splits their built-in transcripts into lines on sentence ends and pauses, marks the obvious cuts (long silences as `pause` / `dead air`, a sentence said again: the earlier take as `retake` of the later, filler-only fragments and restarts as `false start`), keeps the rest, and writes `agent/plan.json` (or `plan.scaffold.json` when a plan exists). **It is a starting point: review every line.** Keep or cut it and say why (`reason`, `why`), choose between takes (`takeOf` links them; keep exactly one), cut tangents and flubs it missed, fix the roles (the first kept line is the hook), and attach visuals per line: an `asset` from the catalog, or `toSource` with a clear description of what to find or make, timed to the words (`at: "croissant"`, `until`). Kept lines play in order, jump cut back to back.
  - **Vlog and 10 Shot: a story of beats** (`mode: "story"`). The beats come after the arc: each with its `role`, timeline frames, the clip and its in-point from your catalog notes, the viewer `takeaway`, and `why` it is here and in this order. Arrange the clips to tell that story, not in file order.
  - Plan to the format's targets (length, change rate, first image or cut, title hook and hold, images per minute, pauses) and checklist; the style skill decides look, type and placement.
- `shred plan <id>` validates it and prints it: a story plan as a beat sheet, a performance plan as a script (timecode in the cut, KEEP or CUT and why, the line, its visuals) with a **To source** list, both with the format's targets estimated. Fix every error (missing media, an in-point past the clip's end, two items on one track at once, a role the format doesn't have, no hook first, two takes of one line kept, a visual with neither asset nor toSource, a word the line doesn't say) and run it again; read the warnings (a line's text not matching its transcript, gaps, length, story order, targets, the plan mode not the format's) and decide. It records the plan's hash; editing the plan means running it again. Give the user the To source list: those visuals are placeholders until someone finds or makes them.
- If the brief says `review.plan: true`: `shred build <id> --markers-only` puts one marker per beat (`<role>: <takeaway>`) or kept line (`<role>: <first words>`), plus a red marker per visual to source, on the user's project, no clips, so they see the structure on the ruler. Walk them through it and wait for their OK; change the plan and repeat if they ask.

### 4. Edit, check, then let the user preview and adjust

- `shred sync <id>` first: the open editor saves now, so the draft includes the user's unsaved tweaks.
- Reuse templates from the library for lower thirds, animated titles and callouts (`shred motion library`, then `addTemplate` with the instance's text and colours), and save new ones the user likes as templates (`shred motion save`; `references/engine.md`, Motion graphics templates).
- A motion graphic the library doesn't have (an animated title, callout, stat hit, logo sting, a full-frame motion piece, or a prompt from `agent/motion-prompts.md`): write it as a HyperFrames composition with the HyperFrames skills, then `shred motion new` / `shred motion add` render it to a transparent overlay on a Motion track (a simple title needs only the starter or a registry block). Read `references/motion.md` first.
- **First pass:** `shred draft <id> --label "..."`, then `shred build <draftId>`: the plan becomes the first assembly in one batch. A story plan: each beat's clip at its frames and in-point, on the format track for its role, camera audio dropped where the format has no sync sound, planned text in the kit's or project's styles, a marker per beat. A performance plan: the kept lines' speaker clips back to back on Speaker (their own audio kept and trimmed with them; lines that run on in the source stay one clip), each visual with an asset on its track over its words, on-screen text, a marker per kept line and a red marker per visual still to source (build lists them: source them, import, and add them in the refine). Open `shred frames` across the beats to confirm the order matches the plan, then refine with `shred apply`. Later passes edit the timeline directly; when the user asks for a restructure (new order, new beats), update `plan.json` and run `shred plan` first. `--no-plan` is only for a first pass on a timeline the user built by hand.
- `shred draft <id> --label "<a few words on what this pass does>"` gives you a private copy. The editor shows the user you're working (with your label) and pauses their editing until you publish. If any shred command says the user stopped the pass, stop and ask them what they want next; if you stop without publishing, run `shred done <draftId>`. Build there in coherent batches (assembly, then type, then callouts, then sound) with `shred apply <draftId> ops.json`. Put each item on the format track for its role (`shred new` printed them: Title, Captions, Images, Speaker, ...); add tracks only for extra layers. Items on one track can't overlap: a batch that would overlap fails whole, so place everything at free ranges. Op shapes, units and gotchas: `references/engine.md`; read it before the first batch.
- Use the project's or the style kit's text styles for titles, labels and captions (`shred styles`), and build captions with `addCaptions`, rather than styling each item by hand.
- Verify on the draft: `shred frames <draftId> --at <frames> --out grid.jpg`, then open it. Sample every shot, both sides of every cut, every text entrance, and anything near the style's safe area. Fix, re-render, look again. Clips that need correction (seen in frames, heard, or prompted by `shred qc`) get it now: colour as an effect, sound as the audio item's EQ/volume (`references/engine.md`, Colour and sound). Nothing gets a correction by default; list what you corrected and why in the summary. Sound: master the voiceover (or the final mix stem) with `shred master <file> --lufs -14 --tp -1.5` and import the `.mastered.wav` it writes; clip volume can't hit a loudness target. Measure the final export with ffmpeg `ebur128` (`references/engine.md`, Loudness). Say if you couldn't listen.
- **`shred check <draftId>` before every publish.** It scores the timeline against the format (and the Video Style Kit, if any) and lists frame ranges for each miss. The format's numbers are guidelines from videos that work, not quotas: a WARN is a prompt to look, and you decide with the video in front of you (say why when you leave one). A FAIL is a rule that makes the video that format, or a kit must: fix it, or tell the user why it stays. A check reading `n/a` means it couldn't measure (say a transcript is missing). With a plan, its Plan section lists beats whose clip is no longer where the plan puts it, beats out of order and length drift: warnings only, since the user's tweaks are decisions. `shred check <draftId> --frames` renders every flagged frame (fails, warns and kit looks) into one contact sheet: open it, judge face, placement and readability yourself, and report the look checks by id.
- Write `summary.md` (template in `references/brief-and-plan.md`): what this pass does, what to look at and when, checks performed, what's placeholder.
- `shred publish <draftId> <id> --label "<one line>" --summary summary.md`. It prints the scorecard and saves it with the pass. On the first publish, open the editor link it prints (the user's project, not the draft; see Setup); after that make sure your browser is still showing it. The editor reloads the pass in about a second.
- Hand over: tell the user the pass is in the editor, give the times worth watching and any scorecard misses, and invite them to adjust anything directly (trim, move, retime, swap, edit text) and save, or to tell you what to change. Then stop and wait.

### 5. Iterate until done

- When the user comes back: `shred sync <id>` (the editor saves what it holds), then `shred changes <id>` lists what they changed since your last pass. Those are decisions; build on them.
- `shred notes <id>` lists their open notes: the Notes tray under the timeline ruler (a drag across it notes a stretch, a double-click or N notes a moment), each with what sits at that frame or range and what they had selected, plus general notes from the Notes tab in Project specs. A note follows the clip it was left on, so its frames are where that moment is now; `trimmed` means its moment was cut out of the clip. A reopened note shows your last answer: that attempt didn't land, try something else. When the user says "check my feedback", "see my comments" or "read my timeline notes" (the Notes tray copies a prompt that says so, with the project id), this is where it is. Listing them marks them picked up: the tray stops pulsing for them. Go to each frame (`shred frames`), act on it in the pass, and once the pass that addresses it is published mark it done with `shred notes <id> --read <id,...> --reply "<what you did, in a line>"` (`--read all` for every open note). The reply and the latest pass label stay on the note: the tray hides it, and the user can show done notes and read your answer, or reopen it. Say in the hand-over which notes you acted on and any you didn't, and why.
- While you wait for the user, `shred notes <id> --watch` (run under a monitor, it never exits) prints one line per note the moment they send it, so their comments reach you without them coming back to the chat. Let a few arrive before starting a pass unless one is urgent.
- It lists markers (added, moved, relabelled) and in/out points too. Markers are often the user's notes to you: read each label and go to its frame.
- The user may undo a whole pass with Cmd+Z: each pass is one undo step in the editor, named by its label. `shred changes` then says the pass was undone (its changes reverted) and lists anything they did after. Respect it: don't reapply that pass unless they ask; the next draft starts from the undone state.
- Scope the next pass to what they asked. `shred draft <id> --label "..."` again (from their current state), apply, verify, `shred check`, publish with a new label, hand over, wait.
- If `shred publish` refuses because they saved while you worked, or because they chose "Edit anyway" in the editor, take a new draft from their state, re-apply your ops, verify, publish.
- **Variants (cuts).** An alternate (another hook, a landscape version, a shorter one) is a new cut, not a pass over the cut the user is reviewing: `shred cut new <id> --label "Hook B"` (`--size 1920x1080` for another aspect: read what it lists to review and fix it in the cut's first pass), then draft, apply, check and publish on the cut's own id as usual; a draft of a cut publishes only into that cut. Name cuts by what differs ("Hook B", "16:9", "30s"), never "v2". Tell the user which cut to look at: their editor stays on the cut they have open, and the cut switcher beside the format chip lists them all (`shred cut list <id>`). `shred cut remove <cutId> --yes` only when they ask. Details: `references/engine.md`, Cuts.
- Repeat until they say it's done. Then export if asked: `shred sync <id>`, then `shred export <id>` (native ffmpeg render from the original media when possible, else the browser render; it prints which items went native and which the browser drew; `--codec prores|hevc` for 10-bit masters). The file lands in `<workspace>/projects/<id>/exports/`. Report the final revision, the export path and engine, the last scorecard, what was checked, and anything unresolved.

## Report format (every pass)

Pass label and revision · format and variant · what changed, in a few lines · times to watch · scorecard (fails and warns, each fixed or explained) · checks actually performed (visual, listened, measured, not checked) · placeholders and open questions.
